# 논문 구성안 — 재난대응 트랙 투고용

이 문서는 대화에서 정한 논문 구성을 옮겨둔 것이다. 다른 PC·다른 세션에서

## 1. 제목

> **재난대응 센서망을 위한 Starlink 백홀 기반 LoRaWAN 구조 제안 및 지연 분석**

영문: *A Satellite-Backhauled LoRaWAN Architecture for Disaster-Response Sensor
Networks and Its Latency Analysis*

### 제목을 이렇게 정한 이유

- **"제안 및 분석"** — 측정 특성화 논문으로 쓰면 표본 1대·단기 관측이 치명적
  약점이 된다. **구조 제안 + 사례 평가**는 그게 정상 형태다.
- **"재난대응"** — 투고 트랙. 그리고 R0·R4·R5 요구사항이 재난 맥락에서
  "편의"가 아니라 "필수"로 격상된다.
- **VPN 을 제목에 넣지 않는다** — Tailscale 은 구성 요소이지 제안의 주인공이
  아니다. 넣으면 "VPN 쓴 게 뭐가 새로운가"라는 공격을 자청한다.

## 2. 기여 선언 (서론 말미)

1. CGNAT 위성 회선 환경에서 **포트포워딩 없이 재배치 가능한 LoRaWAN 백홀
   구조 제안** — 게이트웨이 이동 시 현장 설정 변경 불요
2. 데이터 평면과 분리된 **계측 평면을 구조에 내장**, 운영 중 백홀 지연·가용성
   상시 관측
3. 제안 구조의 실측 평가 — **상·하행 비대칭 87 ms** 확인,
   `RTT/2` 추정이 상행을 **32 % 과소평가**함을 정량화
4. **운용 장애 모드 식별과 자가 복구 설계** — 회선 전환 시 UDP 소켓 고정에
   의한 무음 데이터 손실, `ackr=0` 기반 탐지

> **3번이 가장 강하다.** 서로 독립적인 두 계측(프로브 138.0 ms ↔ GPS 종단
> 143.8 ms)이 6 ms 내로 맞물린다. 방법론 논문의 설득력은 여기서 나온다.

## 3. 설계 요구사항 — III장의 출발점

각 설계 결정이 어떤 요구에서 나왔는지 보여야 "제안"이 성립한다.
**모두 실제로 부딪힌 문제에서 도출됐다.**

| | 요구사항 | 재난 맥락의 근거 | 대응 설계 |
|---|---|---|---|
| **R0** | 사전 네트워크 구성 없이 즉시 전개 | 현장 인프라가 없거나 파괴됨 | 위성 백홀 |
| R1 | 유선 백홀 불가 현장 ↔ 중앙 서버 | 지상 중계 구간 마비 | Starlink |
| R2 | 공인 IP·포트포워딩 불가 (CGNAT) | 현장에서 회선 협의 불가 | 오버레이 네트워크 |
| R3 | Semtech UDP 는 **인증·암호화 없음** | 재난 시 위조 경보 주입은 치명적 | 터널 내부 전달, 공개 바인딩 제거 |
| R4 | **현장에서 설정 변경 불요** | **재난 현장에 엔지니어가 없다** | 오버레이 주소를 목적지로 고정 |
| R5 | 무인 자동 복구 | 접근 불가 지역 설치 | 소켓 재생성 + 워치독 2중 복구 |
| R6 | 백홀 품질 상시 확인 | 경보 전달 가능 여부 실시간 판단 | 데이터/계측 평면 분리 |
| R7 | 경보 전달 지연 상한 충족 | 재난 경보는 허용 한계가 있음 | 측정으로 검증 (V장) |

R3·R6·R7 은 **LoRaWAN 프로토콜 자체의 성질에서 도출**되므로 "그냥 VPN 썼다"와
분명히 구별된다.

## 4. 장 구성

### I. 서론 (4단락)

1. **재난 시 지상 통신 인프라가 먼저 끊긴다** — 지진·침수·태풍으로 유선과
   이동통신 기지국이 정전·단선으로 마비. 그런데 센서 데이터가 가장 필요한
   시점이 바로 그때다(침수 수위, 사면 변위, 구조물 변형, 가스 누출).
   감시가 필요한 순간에 전달 경로가 사라지는 역설.
2. **LoRaWAN 은 적합하지만 백홀이 지상 인프라에 묶여 있다** — 저전력·장거리로
   기지국 없이 광역 배치가 가능하나, 게이트웨이→네트워크 서버 구간은 여전히
   유선/이동통신 의존. **재난 시 단절되는 지점이 정확히 여기다.**
3. **위성 인터넷이 공백을 메울 수 있으나 미검증** — (a) CGNAT 에서 도달성 확보
   방법, (b) 지연·가용성이 **LoRaWAN RX1 1초 제약**을 만족하는지,
   (c) 무인 운용에서 회선 장애 자동 복구 여부.
4. **기여 4개** (§2)

### II. 관련 연구 및 기존 방식의 한계

- LEO 위성 인터넷 지연 특성 연구
- 편도 지연 측정 기법과 **대칭 가정의 문제** (OWAMP, NTP)
- LoRaWAN 백홀 구성 방식

**대안 비교 — 이 장이 비면 "그냥 VPN 썼다"로 읽힌다. 반드시 채울 것.**

| 방식 | R2 (CGNAT) | R3 (무인증 보호) | R4 (재배치) | R5 (자가복구) | R6 (계측) |
|---|---|---|---|---|---|
| 공인 IP + 포트포워딩 | ✗ 고정 IP 필요 | ✗ 공개 노출 | ✗ 현장 재설정 | ✗ | ✗ |
| UDP 1700 직접 노출 | ✗ | **✗ 위조 주입 가능** | ✗ | ✗ | ✗ |
| 순수 WireGuard | △ 엔드포인트 필요 | ○ | △ | ✗ | ✗ |
| 상용 LoRaWAN 클라우드 | ○ | ○ | ○ | △ | ✗ 내부 관측 불가 |
| **제안 구조** | ○ | ○ | ○ | ○ | ○ |

### III. 제안 아키텍처

- 3.1 설계 요구사항 (§3 의 R0~R7)
- 3.2 전체 구조 — **그림 1**
- 3.3 구성 요소 — 게이트웨이 / 위성 백홀 / 오버레이 / 네트워크 서버 / 응용
- 3.4 재배치 가능 설계 (R4)
- 3.5 장애 복구 설계 (R5)
- 3.6 **계측 평면 설계** (R6) — 4-타임스탬프 교환, GPS 절대시각 결합,
  **식 (1)~(3)**

```
식 (1)  RTT    = (t4 − t1) − (t3 − t2)            시계 오차와 무관
식 (2)  offset = ((t2 − t1) + (t3 − t4)) / 2      시계차 + 경로비대칭/2
식 (3)  비대칭  = (offset − 실제시계차) × 2
```

## 6. 5.7절 — 재난대응 요구 충족 여부

재난대응 트랙에서 심사자가 가장 보고 싶어 할 부분.
**"적합/부적합"을 용도별로 갈라서 결론 내는 것이 핵심이다.** 뭉뚱그려
"충분하다"고 하면 공격받는다.

| 측정값 | 재난대응 관점 해석 |
|---|---|
| 상행 138 ms | 경보 전달에 충분. 인지·대응 시간 대비 무의미한 수준 |
| 최장 끊김 20 s | **경보가 최대 20초 지연.** 수위·사면 변위처럼 느린 현상에는 충분하나, 가스 폭발·급류 등 초 단위 대응에는 부족 |
| 가용률 97.46 % | 하루 약 37분 사각. **단일 백홀로는 불충분** → 이동통신 병행 등 이중화 필요 |
| RX1 여유 (p99 264 ms) | 현장 액추에이터 제어(경보기·차단기) 가능 |
| 버퍼링 부재 | **재난 기록 보존 관점의 결함.** 끊김 중 데이터 복구 불가 |

## 7. 한계 절에 반드시 쓸 것 (심사 방어)

숨기면 심사자가 찾아내서 더 크게 지적한다. 먼저 밝히는 게 유리하다.

1. **관측 기간** — 157분·단일 날짜. 위성 배치·기상·시간대 변동 미반영.
   24시간 이상 재측정을 향후 과제로.
2. **시계차 7 ms 의 근거가 NTP 다** — 본문은 "위성 경로의 NTP 는 비대칭 때문에
   믿기 어렵다"고 주장한다. 같은 논리로 7 ms 도 흔들린다.
   **→ 비대칭을 단일 값이 아니라 `87 ± 20 ms` 범위로 제시하고, PPS 배선을
   향후 과제로 둘 것.** 이 처리가 가장 중요하다.
3. **n = 1** — 게이트웨이·장소·회선 각 1개. DERP 표본 54건으로 "+11 ms" 는
   약하게 지지됨.
4. **통제되지 않은 LoRa 트래픽** — 관측 노드가 미등록 제3자 기기,
   SF12·SNR −15 dB 약전계.
5. **다운링크 미실측** — RTT 기반 추론. 실측하면 기여가 크게 올라간다.
6. **실제 재난 현장 시험 없음** — 대전 고정 설치에서 회선만 Starlink 로 변경.
   논문 성격은 **"재난대응 적용을 위한 타당성 검증"**.
7. **가용률은 5초 해상도 기준** — 그보다 짧은 순단은 탐지되지 않는다.
   Starlink 앱이 보고하는 1~2초급 순단은 이 측정의 사각지대다.
