# 측정 발견 사항 기록

이 파일은 측정 과정에서 드러난 사실을 남긴다. 대부분 **해보기 전에는 몰랐던 것**이고,
몇 개는 보고서에 그대로 쓸 수 있는 결과다. 새 발견이 나오면 날짜와 함께 아래에 추가한다.

관련 문서: [protocol.md](protocol.md) · [server.md](server.md) · [rak.md](rak.md)

---

## 1. 스타링크는 상·하행이 크게 비대칭이다 (2026-09-27)

**가장 중요한 결과.**

| 측정값 | |
|---|---|
| RTT | 약 **186 ms** (170~211 ms) |
| 프로브가 계산한 offset | 약 **42 ms** |
| 서버 시계 (구글 NTP 대비 실측) | 약 **−5 ms** |
| 게이트웨이 시계 (`ntpq -pn`) | 약 **−12 ms** |
| → 실제 시계 차이 | 약 **+7 ms** |
| → **비대칭 성분** | **42 − 7 ≈ 35 ms** |

`offset = 실제_시계차 + (상행 − 하행) / 2` 이므로 **상행이 하행보다 약 70 ms 느리다.**

```
RTT = 상행 + 하행 = 186 ms
상행 − 하행 = 70 ms
──────────────────────────
상행 ≈ 128 ms     하행 ≈ 58 ms
```

서버가 독립적으로 관측한 `t2−t1 ≈ 132 ms` 와 일치한다(128 + 시계차 7 = 135).
**서로 모르는 세 곳에서 나온 숫자가 맞물린다.**

### 따라서 `RTT / 2` 를 편도 지연으로 쓰면 안 된다

`RTT/2 = 93 ms` 인데 실제 상행은 약 128 ms다. **38 % 과소평가**한다.
위성 링크에서 편도 지연이 필요하면 GPS 절대시각 기반(§7)으로 재야 한다.

### 4-타임스탬프 설계가 아니었으면 놓쳤을 결과

단순히 "게이트웨이에서 GPS 시각을 보내고 서버 도착 시각과 뺀다"는 방식이었다면
이 42 ms 를 **시계 오차로 오해**했을 것이다. 왕복 교환이었기 때문에 시계 성분과
경로 성분을 분리할 수 있었다.

## 2. NTP 자체도 같은 함정에 빠져 있다 (2026-09-27)

NTP의 오프셋 계산식도 경로 대칭을 가정한다. 따라서 **스타링크 위에서는 ntpd 가
보고하는 오프셋도 신뢰 구간이 넓다.**

게이트웨이 `ntpq -pn` 출력에서 그 증거가 그대로 보였다.

```
 115.15.44.33    delay 189.984   offset +44.770   <- 지연 긴 피어는 오프셋도 튄다
*194.0.5.123     delay  30.762   offset -12.003   <- ntpd 가 최단 경로를 선택 (올바른 동작)
```

지연이 긴 경로일수록 오프셋 추정이 망가진다. 실무 결론: **위성 링크 위의 NTP 값은
±10 ms 이상 믿지 말 것.** 정밀한 시각 기준이 필요하면 GPS/PPS 를 써야 한다.

참고로 국내 NTP 서버인데도 delay 가 30~190 ms 로 나온다. 모든 트래픽이 위성 경로를
돌고 있다는 뜻이다. 일부 피어는 `reach` 가 `177`·`357`·`217` 로 패킷을 흘리고 있다
(프로브는 같은 구간에서 손실 0 %).

## 3. 회선이 바뀌면 UDP 소켓이 죽는다 — 무인 운용의 최대 위험 (2026-09-23)

사내 LAN → 스타링크로 회선을 바꾼 뒤 **LoRa 데이터와 프로브가 동시에 끊겼다.**
Tailscale 터널은 정상이었고 `tailscale ping` 도 왕복했다.

### 증상

```
"rxnb":9,"rxok":0,"rxfw":0,"ackr":0.0,"dwnb":0,"txnb":0
```

`ackr: 0.0` — 서버가 PUSH_DATA 를 하나도 확인응답하지 않았다.
패킷포워더는 `JSON up:` 로그를 계속 찍고 있었지만 패킷은 허공으로 나갔다.

### 원인

```
192.168.1.70:60157 -> 100.84.186.95:1700   lora_pkt_fwd
192.168.1.70:59167 -> 100.84.186.95:1800   python3 (probe)
```

출발지가 **스타링크 공유기의 LAN 주소(`192.168.1.70`)** 로 잡혀 있었다.
목적지는 Tailscale 주소이므로 출발지도 `100.112.121.22` 여야 한다.

UDP 소켓은 `connect()` 시점에 경로를 한 번 결정하고 출발지를 **고정**한다.
회선 전환 중 `tailscale0` 경로가 잠시 내려갔고, 그 사이 재조회가 기본 경로로
떨어져 거기에 박혔다. 프로세스는 살아 있으므로 systemd `Restart=always` 도
발동하지 않는다. **조용히 죽는다.**

### 조치와 남은 과제

두 서비스를 재시작하면 복구된다.

```bash
sudo systemctl restart ttn-gateway
sudo systemctl restart lora-probe
```

**이건 임시방편이다.** 베트남 무인 운용에서는 회선이 한 번 깜빡일 때마다 사람이
가야 한다는 뜻이므로, 자동 복구가 필요하다. 후보:

- 프로브: `connect()` 를 쓰지 않거나, 연속 타임아웃 시 소켓을 재생성
- 패킷포워더: 상용 C 코드이므로 `ackr` 이 0 인 상태가 지속되면 재시작하는 워치독
- 공통: `systemd` 의 네트워크 변경 훅 활용

### 진단 시 볼 것

| 신호 | 의미 |
|---|---|
| `ackr: 0.0` | 서버 미도달. 가장 빠른 신호 |
| `ss -unp` 의 출발지 주소 | Tailscale 주소가 아니면 소켓이 잘못 박힌 것 |
| `tailscale ping` 은 되는데 데이터는 안 옴 | 터널이 아니라 애플리케이션 소켓 문제 |

## 4. 시계 실측값 (2026-09-27)

| 대상 | 방법 | 값 |
|---|---|---|
| 서버 (`aeron-sever`) | `w32tm /stripchart` vs time.google.com | **−3 ~ −7 ms** |
| 게이트웨이 (`rak7248-gw`) | `ntpq -pn` 선택 피어 | **약 −12 ms** |

서버는 2026-09-22 에 NTP 소스를 `time.windows.com`(폴링 1024초)에서
`kr.pool.ntp.org` · `time.google.com` · `time.cloudflare.com`(폴링 64초)로 교체했다.

### 루트 분산은 실제 오차가 아니다

교체 직후 `w32tm /query /status` 의 **루트 분산이 1.78초 → 7.77초로 오히려 올라갔다.**
그러나 같은 시점 실측 오차는 **3~7 ms** 였다.

루트 분산은 보수적인 **상한 추정치**이고 서비스 재시작으로 내부 상태가 초기화되면
크게 잡힌다. Windows 에서 이 값을 실제 정확도로 읽으면 안 된다.

## 5. 기준선 비교 — 회선이 바뀌면 이렇게 달라진다

| | 사내 LAN (~09-23) | 스타링크 (09-27~) |
|---|---|---|
| RTT | 약 **8 ms** (2.8~14) | 약 **186 ms** (170~211) |
| 겉보기 편도 (`t2−t1`) | 4~7 ms | 125~145 ms |
| 지터 | 2~3 ms | 약 20 ms |
| 경로 | `direct` 안정 | `direct` ↔ `derp` 전환 |
| 손실률 | 0 % | 0 % |
| 서버 처리시간 | 50~80 µs | 50~80 µs (변화 없음) |

LAN 시절 RTT 분산(2.8~14 ms, 5배)은 네트워크가 아니라 **양 끝단 스케줄링 지연**으로
보인다. 스타링크에서는 실제 경로 지연이 그보다 훨씬 커서 상대적으로 묻힌다.

## 6. `direct` 와 `derp` 를 절대 섞지 말 것

스타링크는 CGNAT 를 쓰기 때문에 Tailscale 이 직접 연결을 유지하기 어렵고,
**`direct` 와 `derp`(릴레이) 사이를 오간다.** 두 상태는 지연 분포가 근본적으로 다르다.

섞어서 평균 내면 아무 의미 없는 숫자가 나온다. 분석 시 반드시 `path` 로 나눌 것.
그래서 프로토콜에 `path` 필드를 넣었다([protocol.md](protocol.md) §7).

## 7. LoRa 업링크에 GPS 시각이 실려 온다 (2026-09-27)

게이트웨이 레벨 `UplinkFrame` 을 디코딩해 확인했다.

```
gw_time              : 2026-09-27 06:32:15.060570   <- GPS 유래, 무선 수신 순간
time_since_gps_epoch : 17066 days, 6:32:34.060000
fine_time_since_gps  : 없음
```

**`gw_time` 은 GPS 절대시각**이므로, 이걸 쓰면 §1 의 비대칭 문제를 우회해
**대칭 가정 없이 진짜 상행 편도 지연**을 잴 수 있다. `probe/e2e_logger.py` 가 이를 기록한다.

`fine_time_since_gps_epoch` 는 없다 → 나노초급 도착시각이 필요한 용도(TDOA 측위 등)는 불가.

## 8. 측정 인프라 설계에서 걸린 함정들

### Docker 포트 프록시가 측정에 섞인다

Docker Desktop 은 Windows → WSL2 VM → 컨테이너로 포트를 중계한다. 컨테이너 안에서
프로브에 응답하면 **네트워크가 아니라 Docker 프록시를 재게 된다.** 그래서 응답기와
종단 지연 기록기 모두 **Windows 네이티브**로 실행한다.

단, 실제 LoRa 데이터는 이 프록시를 한 번 더 지난다. 프로브 값은 **네트워크 경로의
하한**이며 LoRa 종단 지연은 이보다 크다.

### 컨테이너 시계를 기준으로 쓰면 안 된다

컨테이너 시계가 호스트와 얼마나 맞는지는 `docker exec` 시작 오버헤드(약 200 ms)에
묻혀서 정밀하게 확인하기 어렵다. **모든 측정 타임스탬프를 호스트 시계로 통일**했다.
프로브가 재는 오프셋이 호스트 기준이므로 보정값을 그대로 적용할 수 있다.

### Tailscale 노드 식별은 이름이 아니라 IP 로

`HostName` 은 OS 호스트명(`WIN-OB5FI29VAFC`), `DNSName` 은 콘솔에서 바꾼 이름
(`aeron-sever`)으로 **서로 다르다.** 이름으로 매칭하면 노드 이름을 바꾸는 순간
조용히 깨진다. 실제로 첫 구현이 이 때문에 `path` 를 계속 `unknown` 으로 기록했다.

또 `CurAddr` 가 채워진 direct 상태에서도 `Relay` 필드에 폴백 후보(`tok`)가 들어 있다.
**`Relay` 만 보고 판정하면 direct 를 derp 로 오인한다.** `CurAddr` 우선으로 볼 것.

### 대시보드는 이미지에 소스를 굽는다

`dashboard/` 아래를 고치면 `docker compose up -d --build dashboard` 로 **재빌드**해야
반영된다. `restart` 나 `up -d` 만으로는 안 바뀐다.

## 9. `gw_time` 은 시스템 시계보다 약 1.03 초 뒤처진다 (2026-09-27)

`e2e_logger.py` 의 `recv − gw_time`(`raw_ms`)이 **약 1167 ms** 로 나왔다.
네트워크 상행 지연(약 128 ms)의 9 배다.

### 원인 규명 과정

**1단계 — time-on-air 가 아니다.**

| | 범위 | 폭 |
|---|---|---|
| `raw_ms` | 1151.4 ~ 1182.6 ms | **31 ms** |
| `toa_ms` | 370 ~ 3285 ms | 2974 ms |

SF10~12 에서 전파 시간이 10 배 가까이 차이 나는데 `raw_ms` 는 꿈쩍도 하지 않는다.
→ **`gw_time` 은 수신 '끝' 시점이 맞고**, 큐잉도 아니다(큐잉이면 꼬리가 길게 늘어진다).

**2단계 — 두 DB 를 대조해 시계 성분을 분리.**

```
raw_ms      = 상행지연 + (호스트시계 − 게이트웨이 GPS시계)
프로브 t2−t1 = 상행지연 + (호스트시계 − 게이트웨이 시스템시계)
────────────────────────────────────────────────────────────
raw_ms − (t2−t1) = 게이트웨이 시스템시계 − GPS시계
```

시각이 가까운 표본끼리 짝지어 계산한 결과(34 건):

```
평균 1029.4 ms · 중앙값 1030.3 ms · 범위 1003 ~ 1045 ms
```

### 결론 — PPS 가 없기 때문이다

게이트웨이에 **`/dev/pps0` 가 없다**(§ [rak.md](rak.md) §2 조사 결과). PPS 없이 NMEA
문장만으로 시각을 잡으면, NMEA 는 자기가 가리키는 PPS 엣지보다 **약 1 초 늦게**
시리얼로 도착한다. 그 지연이 그대로 `gw_time` 에 실린다.

### 실무상 의미

| | |
|---|---|
| **절대 종단 지연** | `raw_ms − 1030 ms` 로 보정해야 유효 |
| **변동분(지터·스파이크)** | **보정 없이도 그대로 유효** |
| 근본 해결 | 게이트웨이에 PPS 배선 + chrony PPS refclock |

보정 상수는 고정값이 아닐 수 있으므로(GPS 수신 상태에 따라 변동 가능),
장기 측정 시 주기적으로 재측정하는 것이 안전하다.

## 10. 회선 끊김 추적 (2026-09-27 추가)

스타링크가 주기적으로 끊기므로 `/api/probe/outages` 로 끊김 구간을 복원한다.
프로브 수신 시각(`t2`)의 간격이 정상 주기의 **2.5 배** 이상 벌어지면 끊김으로 판정한다.

- **해상도 한계는 프로브 주기(10 초)** 다. 그보다 짧은 순단은 잡히지 않는다.
- 정상 주기는 **중앙값**으로 잡는다. 평균을 쓰면 끊김 구간이 임계값을 밀어올린다.
- `run` 이 바뀐 구간은 회선 문제가 아니라 게이트웨이 프로세스 재시작이다.
- 산출: 끊김 횟수 · 총 끊김 시간 · 최장 끊김 · **가용률** · 경로 전환 횟수

### `unknown` 표본은 경로 전환에서 제외할 것

게이트웨이가 `tailscale status` 를 못 읽은 표본은 `path="unknown"` 으로 남는다.
이걸 그대로 두면 `direct → unknown → direct` 가 **전환 2 회로 잡혀** 분석이 오염된다.
마지막으로 '확인된' 경로와만 비교해야 한다. 실제로 첫 구현에서 허위 전환 3 회가
잡혔고, 필터링 후 실제 1 회(`derp → direct`)로 정정됐다.
