# 정비 이력

측정 중 **운용자가 유발한 중단**을 기록한다. 회선·장비 장애가 아니므로
**가용성 통계에서 제외해야 하는 구간**이다. 기록하지 않으면 나중에 데이터를
다시 볼 때 스타링크 끊김으로 오해한다.

새 정비 작업은 아래에 **역순(최신 위)** 으로 추가한다.
자동 기록: `probe/maintenance.ps1` 을 거쳐 로거를 멈추면 시각이 자동으로 남는다
(`probe/log/maintenance.log`).

| 항목 | 내용 |
|---|---|
| 작업 | `probe/data` → `probe/live` 로 라이브 DB 이전, 로거 중지·재시작 |

| 영향 프로세스 | `probe_server.py` (응답기), `e2e_logger.py` (LoRa 종단) **둘 다** |

### 영향 구간 — 가용성 산정에서 제외할 것

| 대상 | 공백 (UTC) | 길이 | 유실 |
|---|---|---|---|
| 프로브 (`probe_rx`) | `09:17:03.564` ~ `09:17:09.562` | **6.00 s** | `seq 6229~6233` **5건** |
| LoRa 종단 (`e2e`) | `09:17:04.479` ~ `09:17:09.021` | **4.54 s** | **52건** |

KST 로는 각각 `18:17:03.564~18:17:09.562`, `18:17:04.479~18:17:09.021`.
해당 run 은 `1792481586`.

### 귀속 근거 — 서버 측, 운용자 유발

**두 프로세스는 서로 별개다**(`probe_server.py` / `e2e_logger.py`). 같은 시각에
공백이 생긴 것은 **같은 정비 창에서 둘 다 중지했기 때문**이다.

게이트웨이는 그 동안 **정상 송신했다.** 게이트웨이 측 DB 에는 `lost=1` 로 남고,
서버 측에는 `seq` 구멍으로 남는다. 계층별 대조로 "서버 측 원인"이 확정된다.

LoRa 측은 **실제 유실이 아니라 기록 누락**이다. 게이트웨이 브리지 로그가
공백 창 내내 업링크를 계속 발행한 것을 보여준다.

```
09:17:02  10건    09:17:06  10건
09:17:03  11건    09:17:07  12건
09:17:04  13건    09:17:08  10건
09:17:05  12건    09:17:09  13건
```

공백 창(`09:17:04.479~09:17:09.021`) 안에서 브리지가 발행한 업링크는 **52건**이고,
첫 건 `09:17:04.556`, 끝 건 `09:17:09.021` 이다. MQTT 는 QoS 0 이고 지속 세션이
아니므로 **그 52건은 복구할 수 없다.** 다만 존재는 브리지 로그로 입증된다.

### OS 로그로는 보강되지 않는다

| 로그 | 결과 |
|---|---|
| 작업 스케줄러 Operational | 기록 없음 (해당 채널 기본 비활성) |
| 프로세스 생성·종료 감사 (4688/4689) | 미활성 (Windows 기본값) |
| System (Service Control Manager) | `18:17:33` 이후만 — 공백 구간보다 **늦음** |

**원인 귀속은 계층별 기록 대조로만 성립한다.** 논문에서는 이 점을 약점으로 쓰지
말고 **계측 평면의 효용**으로 쓸 것 — 제안 구조가 장애 구간을 스스로 귀속시킬 수
있음을 보여주는 사례다 (paper-outline.md 3.6 절).
