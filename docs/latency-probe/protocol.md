# LoRa 게이트웨이 ↔ 서버 지연 측정 프로브 — 프로토콜 규격

서버와 게이트웨이 양쪽 구현이 **반드시 이 문서를 기준으로** 맞춰져야 한다.
한쪽만 바꾸면 측정값이 조용히 틀어지므로, 변경 시 이 문서를 먼저 고치고 양쪽에 반영한다.

## 1. 목적

Tailscale 터널을 통과하는 게이트웨이 ↔ 서버 경로의 **왕복 지연(RTT)**, **편도 지연 추정치**,
**두 장비의 시계 오프셋**, **패킷 손실**을 주기적으로 측정해 기록한다.

## 2. 왜 4개의 타임스탬프인가

단순히 "게이트웨이에서 GPS 시각을 찍어 보내고 서버 도착 시각과 뺀다"는 방식은 **작동하지 않는다.**
서버(`aeron-sever`) 시계의 오차 한계(root dispersion)가 측정 시점 기준 **약 1.8초**인데,
측정하려는 지연은 **약 6ms**(같은 LAN 기준)다. 신호보다 노이즈가 300배 크다.

NTP와 동일한 4-타임스탬프 교환을 쓰면 두 시계의 오프셋이 수식에서 상쇄되어,
**시계 동기화 없이도 지연을 정확히 구할 수 있다.** 오프셋은 덤으로 측정 결과물이 된다.

```
게이트웨이                                     서버
  t1 (송신) ────────  req(seq, t1)  ────────▶  t2 (수신)
  t4 (수신) ◀───── rsp(t1, t2, t3)  ────────   t3 (송신)
```

| 값 | 계산식 | 의미 |
|---|---|---|
| RTT | `(t4 - t1) - (t3 - t2)` | 서버 처리시간을 제외한 순수 왕복 지연 |
| 편도 추정 | `RTT / 2` | 경로가 대칭이라는 가정 하의 편도 지연 |
| 시계 오프셋 | `((t2 - t1) + (t3 - t4)) / 2` | 서버 시계 − 게이트웨이 시계 |

**중요:** `RTT`는 두 시계의 오프셋과 무관하다. 반면 `편도 추정`은 경로 대칭성을,
`오프셋`은 경로 대칭성을 가정한다. 비대칭 경로(예: DERP 릴레이 경유)에서는
오프셋 추정에 편향이 생기므로, 아래 `path` 필드를 반드시 같이 기록한다.

## 3. 전송 규격

| 항목 | 값 |
|---|---|
| 프로토콜 | UDP |
| 서버 주소 | `100.84.186.95` (Tailscale, 노드 `aeron-sever`) |
| 서버 포트 | `1800` |
| 클라이언트 | `rak7248-gw` (`100.112.121.22`) |
| 인코딩 | UTF-8, 개행 없는 단일 라인 JSON |
| 최대 크기 | 512 바이트 |
| 기본 주기 | 10초 |
| 응답 타임아웃 | 2초 |

포트 `1800`은 2026-09-22 기준 서버에서 미사용 상태를 확인했다.
LoRa 데이터 경로(`1700/udp`)와는 완전히 분리된 별도 채널이다.

## 4. 메시지 형식

### 4.1 요청 (게이트웨이 → 서버)

```json
{"v":1,"typ":"req","run":1758500000,"seq":1234,"src":"rak7248-gw","t1":1758505123456789012,"tsrc":"gps","path":"direct"}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| `v` | int | 프로토콜 버전. 현재 `1`. 다르면 무시한다 |
| `typ` | str | `"req"` 고정 |
| `run` | int | 프로세스 시작 시각(Unix 초). 재시작 시 `seq`가 0부터 다시 시작하므로 이걸로 구분 |
| `seq` | int | 0부터 1씩 증가. 손실 판정의 기준 |
| `src` | str | 송신 노드명 (`"rak7248-gw"`) |
| `t1` | int | 송신 시각. **Unix epoch 기준 나노초** |
| `tsrc` | str | `t1`의 시각 출처. `"gps"`(GPS 동기 시계) 또는 `"sys"`(일반 NTP) |
| `path` | str | 송신 시점 Tailscale 경로. `"direct"` 또는 `"derp"` |

### 4.2 응답 (서버 → 게이트웨이)

```json
{"v":1,"typ":"rsp","run":1758500000,"seq":1234,"t1":1758505123456789012,"t2":1758505123462100000,"t3":1758505123462180000,"srv":"aeron-sever"}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| `v` `typ` | | `1` / `"rsp"` |
| `run` `seq` `t1` | | 요청에서 받은 값을 **그대로 에코** |
| `t2` | int | 서버 수신 시각 (ns). `recvfrom` 반환 **직후** 찍는다 |
| `t3` | int | 서버 송신 시각 (ns). `sendto` 호출 **직전**에 찍는다 |
| `srv` | str | 응답 노드명 (`"aeron-sever"`) |

### 4.3 구현 시 반드시 지킬 것

- **`t2`는 수신 직후, `t3`는 송신 직전.** 그 사이에 디스크 I/O·로깅·파싱을 끼워넣으면
  `t3 - t2`가 부풀어 RTT가 과소평가된다. 로깅은 큐에 넣고 별도 스레드가 처리한다.
- **타임스탬프는 벽시계(wall clock) 나노초.** `t1`/`t4`의 차이는 단조시계(monotonic)로도
  같이 기록해두면 측정 중 NTP 스텝이 발생해도 RTT를 구제할 수 있다 (§6 참고).
- 파싱 실패·버전 불일치·`typ` 불일치 메시지는 조용히 버린다. 절대 예외로 죽지 않는다.
- 서버는 tailnet(`100.64.0.0/10`) 외의 출발지에서 온 패킷은 무시한다.

## 5. 기록 규격

### 5.1 게이트웨이 측 (주 데이터셋)

게이트웨이가 4개 타임스탬프를 모두 가지므로 **분석의 기준 데이터는 게이트웨이 로그**다.

| 컬럼 | 설명 |
|---|---|
| `run` `seq` | 식별자 |
| `t1` `t2` `t3` `t4` | 4개 타임스탬프 (ns). 손실 시 `t2`/`t3`/`t4`는 NULL |
| `rtt_ns` | `(t4-t1)-(t3-t2)`. 손실 시 NULL |
| `offset_ns` | `((t2-t1)+(t3-t4))/2`. 손실 시 NULL |
| `mono_rtt_ns` | 단조시계로 측정한 `t4-t1` (§6) |
| `lost` | 0 = 정상 응답, 1 = 타임아웃 |
| `tsrc` | `"gps"` / `"sys"` |
| `path` | `"direct"` / `"derp"` |
| `relay` | DERP 경유 시 릴레이 지역명, 아니면 빈 문자열 |

### 5.2 서버 측 (교차 검증용)

`run`, `seq`, `src`, `peer`(출발지 IP), `t1`, `t2`, `t3`, `tsrc`, `path`

### 5.3 손실 구분

두 로그를 대조하면 손실 방향을 구분할 수 있다.

| 서버 로그 | 게이트웨이 로그 | 해석 |
|---|---|---|
| 있음 | `lost=0` | 정상 |
| **없음** | `lost=1` | **요청(상행)이 유실** |
| **있음** | `lost=1` | **응답(하행)이 유실** |

## 6. 단조시계 보조 기록

`t1`/`t4`를 벽시계로만 재면, 측정 도중 NTP가 시계를 점프시킬 때 RTT가 터무니없는 값이 된다.
게이트웨이는 송수신 시점에 `time.perf_counter_ns()` 같은 단조시계도 같이 찍어
`mono_rtt_ns = mono4 - mono1`을 별도 컬럼에 남긴다.

- 평상시: `mono_rtt_ns ≈ (t4-t1)` 이어야 정상
- 둘이 크게 어긋난 구간 = 시계 스텝이 일어난 구간 → 분석 시 해당 구간의 `offset_ns`는 버린다

## 7. `path` 필드가 중요한 이유

Tailscale은 직접 연결(`direct`)이 안 되면 DERP 릴레이로 폴백한다.
현재는 `direct`로 RTT 6ms지만, 릴레이를 타면 수십~수백 ms로 뛴다.
이걸 기록하지 않으면 나중에 **설명되지 않는 분산**으로만 보인다.

`tailscale status --json`의 자기 노드 피어 정보에서 `CurAddr`(direct면 채워짐)와
`Relay`(DERP면 지역명) 필드로 판정한다. 매 프로브마다 호출하면 부하가 크므로
**30초~1분 주기로 캐시**하고 그 값을 첨부한다.

## 8. 시각 출처(`tsrc`)에 대한 주의

"GPS니까 무조건 정확하다"는 **틀리다.**

| 구성 | 대략적 정확도 | 비고 |
|---|---|---|
| GPS + PPS + chrony | 마이크로초급 | 이상적 |
| GPS NMEA만 (PPS 없음) | 수십 ms 지터 | 시리얼 전송 지터 때문. **잘 맞춘 NTP보다 나쁠 수 있다** |
| LAN NTP (잘 설정된 경우) | 수 ms | |
| 현재 서버 상태 | **±1.8초** | `time.windows.com`, 폴링 1024초 |

단, §2에서 설명했듯 **RTT는 시계 품질과 무관하다.** 시계 품질은 `offset_ns`와
편도 분해의 신뢰도에만 영향을 준다. 따라서 GPS/PPS 구성이 여의치 않아도 측정은 시작할 수 있고,
`tsrc` 필드에 무엇을 썼는지만 정직하게 남기면 된다.
